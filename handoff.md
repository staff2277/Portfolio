## Research Notes
- **2026-07-31 (2) — Camera_Export baked animation, actual keyframe analysis.** User asked whether the camera moves forward in a straight line on Y, then does a quarter-circle while rising. Parsed `showroom.glb`'s raw keyframe buffer directly (111 keyframes, `animations[0]` = "Camera_ExportAction", targets node 2 = `Camera_Export`, LINEAR interpolation, `translation` + `rotation` channels, duration 4.5833s = 110 frames @ 24fps -- matches `HERO_START`/`HERO_HOLD`/`HERO_END` in `HeroScene.js`). Axis convention: glTF/this export is Y-up, X-right; camera looks down -Z locally.
  - **Frames 0→42 (Phase A range)**: straight line confirmed -- max perpendicular deviation from the start→end line across all keyframes in this range is 0.025 units over an 85.5-unit path (effectively exact). BUT the dominant axis is **Z, not Y**: position goes `(-0.15, 14.90, 115.29)` → `(-0.07, 14.08, 29.73)`. ΔZ = -85.5 (dolly forward), ΔX = +0.08 (~flat), ΔY = -0.82 (slight *drift down*, not up). If "Y axis forward" meant the depth/forward axis colloquially, this holds; if it meant the literal glTF Y (vertical) axis, it does not -- Y is nearly flat here.
  - **Frames 42→110 (Phase B range)**: NOT a quarter circle. Least-squares circle fit to the X-Z path: center ≈ `(2.87, 4.99)`, radius ≈ 19.7. Angular sweep from the fit center goes 96.8° → -99.0°, a **~196° sweep** (more than a half circle, not a quarter). Radius isn't constant either -- ranges ~17.5 to ~26 across the sweep (tightens from 26→17.5 through roughly the first two-thirds, then holds steady ≈ 17.5–21), so it's an eased/slightly-spiraling arc rather than a geometrically perfect circle. Y **does** rise continuously and monotonically the whole time (14.08 → 56.92, +42.8 total) confirming "moving up", but the rise accelerates hard in the back third -- roughly +16.6 over frames 42→90, then +26.2 over just frames 90→110 (ease-in climb, not linear).
  - Full per-frame table (frame, X, Y, Z, fit-radius, fit-angle) generated during this analysis but not saved to disk -- rerun the parse (see method below) if the exact numbers are needed again.
  - **Method** (for reuse, since the Filesystem MCP struggled with this file before): `Filesystem:copy_file_user_to_claude` succeeded this time (11MB, prior attempts had timed out -- seems intermittent/transient, not a hard blocker). Once copied into Claude's own sandbox at `/mnt/user-data/uploads/showroom.glb`, parsed with a plain Python `struct`/`json` GLB reader (12-byte header, JSON chunk, BIN chunk; accessors 8/9/10 = time/translation/rotation for `Camera_ExportAction`). Both Blender MCP tools (`execute_blender_code` live-connection and `execute_blender_code_for_cli`) and the Puppeteer MCP tool were unresponsive/timed out throughout this session and were not usable as alternatives.
  - Side note: node 4 ("Empty") also has an animated translation (`EmptyAction`, accessor 11) in the same glTF animations array, but it's static until roughly frame 90-100 and then only rises in Y (X/Z constant) -- doesn't look like a look-at/aim target for the camera's arc. ### 2026-08-21 (4) — Reusable magnetic button interaction (site-wide)
Implemented the requested magnetic-hover interaction as a single global, reusable module rather than a per-button React wrapper component, to best satisfy "reusable across the website" + "don't alter existing visual design/layout":

- **New file `components/MagneticButtons.js`** (client component, mounted once in `app/layout.js` alongside `SmoothScroll`/`SideProgressBar`, not per-page). On mount it scans the whole document for any element carrying a `data-magnetic` attribute and wires up the effect — **no other markup, structure, or CSS on those elements is touched**, so existing typography/colors/padding/borders/layout are fully preserved. New elements added later (route changes, conditional renders) are picked up automatically via a `MutationObserver`, no manual re-registration needed.
- **Chose GSAP over framer-motion** (Option B from the spec) for consistency with the rest of the codebase — GSAP is already the established physics/animation library here (`SideProgressBar.js`'s magnetic ball, `useCameraScroll.js`'s ScrollTrigger), and `framer-motion` is only used for `WorkSection.js`'s cross-fade. Uses `gsap.quickTo()` (not `gsap.to()` per mousemove) so repeated pointer updates reuse one interpolating tween instead of spawning a new tween every tick — the standard GSAP pattern for smooth, 60fps-safe continuous pointer-following. `force3D: true` on every tween guarantees `translate3d()` (GPU-accelerated, no layout reflow).
- **Proximity-based, not just hover-based:** rather than only reacting once the cursor is directly over the button (`mouseenter`/`mousemove` scoped to the element), a single shared `window` `mousemove` listener (batched through one `requestAnimationFrame` pass per tick, iterating all registered buttons) computes each button's distance from the cursor to its nearest *edge* (0 if the cursor is already inside), and starts pulling once that's within a configurable radius (`data-magnetic-radius`, default 80px beyond the button's own bounding box) — with a falloff so the pull ramps in smoothly across that ring rather than snapping on at the boundary. This matches the spec's "comes within close proximity or hovers directly over" wording more literally than a hover-only trigger would.
- **Displacement capped** at `data-magnetic-max` (default 20px, spec range 15–25px) via `gsap.utils.clamp`, computed from `(cursor − button center) × strength × falloff`, `strength` tunable per element via `data-magnetic-strength` (default 0.35).
- **Elastic snap-back** on leaving the proximity radius (or the window entirely, via a `document` `mouseleave`): `gsap.to(el, { x: 0, y: 0, duration: 0.8, ease: "elastic.out(1, 0.3)" })` — exact easing/duration from the spec.
- **Optional multi-layer parallax polish, opt-in only:** if a `data-magnetic` element contains a descendant tagged `data-magnetic-inner`, that inner element gets its own `quickTo` pair driven at 1.2x the outer offset (own clamp at `maxOffset × 1.2`) for a subtle layered/3D-depth feel. None of the buttons wired up this session use it (their icon/text isn't in a separate layer), but it's there for any future button that wants it without touching this module.
- **Touch/coarse-pointer guard:** everything is gated behind `window.matchMedia("(hover: hover) and (pointer: fine)")` — if it doesn't match on mount, no listeners are attached at all (zero overhead on touch devices, standard tap behavior fully untouched). Also listens for the media query's own `change` event so it enables/disables live if that ever flips (e.g. devtools responsive-mode toggling, or a hybrid device switching input mode) rather than only checking once at load.
- **Wired up on the 4 existing buttons** in `app/page.js` by adding a bare `data-magnetic` attribute — no other change to those elements: the 3 rounded-full icon links (Contact mail icon, X/Twitter, LinkedIn) and the "Say Hello" mailto pill in the contact section.

User should confirm: the pull feels right at the default `strength`/`max`/`radius` values (all first-pass, no authorial spec to tune against beyond the given ranges), the elastic snap-back looks natural, and that nothing regressed on touch/mobile viewports (should be a full no-op there).

### 2026-08-01 (4) — Root cause found: paused AnimationAction silently ignores mixer.setTime()
User reported the new scroll hook (2026-08-01 (3)) still didn't move the camera, but with `[cameraScroll]` console logs showing `progress`/`frame` correctly sweeping 0->110 as they scrolled, and `mixer`/`camera` both truthy -- i.e. the scroll-to-frame math was provably correct, so the bug had to be in how that frame value gets applied.

**Root cause:** `HeroScene.js`'s mixer setup had `action.paused = true` (present since the very first version of this project, carried through every iteration so far -- never actually the bug until now, or more likely always the bug and never isolated before). This is a real Three.js `AnimationAction` internals quirk: `mixer.setTime(t)` resets the action's internal `time` to 0 and then calls `update(t)`, which calls `_updateTimeScale()` -- and that function returns `0` whenever the action is `paused`, which zeroes the delta applied to the clip. Net effect: **a paused action's `setTime()` always evaluates to clip time 0, no matter what value is passed in.** The camera silently never advances past frame 0, while everything upstream (scroll listener, progress math, `mixer.setTime()` call itself) works perfectly -- exactly matching the reported symptom.

**Fix:** removed `action.paused = true` from the mixer setup effect in `HeroScene.js`. Safe to leave unpaused because nothing in this codebase calls `mixer.update()` in a continuous loop (a manually-constructed `AnimationMixer` isn't auto-driven by R3F the way `drei`'s `useAnimations` hook would; only this project's own `mixer.setTime()` calls ever touch it), so there's no risk of the clip "playing" on its own once unpaused.

**Not yet re-verified in the browser by me** (no browser access). This should be the real fix, but user should hard refresh and confirm the camera actually visibly moves now, not just that the console numbers look right (which they already were).
