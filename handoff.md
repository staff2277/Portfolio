### 2026-08-29 (3) — SCROLL_DISTANCE walkback: 4900vh was intentional, 490vh was too fast
User corrected the previous entry's assumption: `"+=4900vh"` in `useCameraScroll.js` was **not** a typo, it was deliberately set to slow down the hero camera's scroll speed. My earlier cut to `"+=490vh"` (part of the initial perf pass) made the camera race through frames too fast. User then asked whether there's a more efficient way to slow the camera than just cranking this number back up.

**Explained to user (worth remembering for next time this comes up):** in the current architecture, camera frame position is a direct linear function of scroll progress (`frame = mapRange(progress, 0, 1, 45, 110)`), and `SCROLL_DISTANCE` is the ratio's denominator. Slower perceived camera motion per unit of scroll input *necessarily* requires more total scroll distance — there's no way to decouple "feels slow" from "takes more scrolling" without manually intercepting wheel/touch events and scaling their delta (i.e. reconstructing the old "wheel-jack" phase). That approach is explicitly documented earlier in this file (2026-07-31/2026-08-01 entries) as having been torn out after causing pinSpacing collapse, momentum-handoff bugs, and non-monotonic scroll progress — not something to casually reintroduce.

**Changes made:**
- `SCROLL_DISTANCE` set to `"+=1800vh"` — a middle-ground starting point between the too-slow 4900vh and the too-fast 490vh. **Not yet confirmed correct by the user** — this is a guess pending browser feedback, not a final tuned value. Whoever picks this up next: check with the user whether 1800vh feels right before treating it as settled, and adjust up/down from there. The constant's comment block explains the speed/distance tradeoff in place so this doesn't get relitigated as a "bug" again.
- `scrub` bumped from `0.3` to `0.5` on the Phase 2 `ScrollTrigger` — adds a bit more lag/smoothing so fast wheel flicks don't snap through frames as abruptly. This is independent of `SCROLL_DISTANCE` and may help the "too fast" feeling somewhat on its own, but is a smoothing tweak, not a substitute for the distance tuning above.

### 2026-08-28 — Rebuilt Work-section transition as continuous scroll-driven crossfade; fixed prev/next click-to-navigate
User feedback on the scale+blur transition from the previous session: (1) disliked that titles/mockup "disappear and reappear" between projects, and (2) clicking prev/next project names in the desktop Work section did nothing — there was no way to navigate between projects by clicking their names.

**Root cause of (1):** the desktop title zones (top/center/bottom) and the right-column browser mockup used Framer Motion `AnimatePresence` keyed off `activeIndex` (an integer React state that only changes when scroll crosses a project boundary). Every index change fully unmounted the outgoing element and mounted a new one with its own enter/exit animation. Under fast or reversed scrubbing, `activeIndex` can update multiple times before an in-flight enter/exit animation finishes, interrupting it mid-flight — which reads as content vanishing then popping back in rather than a smooth morph.

**Root cause of (2):** the prev/next titles (`h3` elements in the top/bottom zones) had no `onClick` at all — they were purely decorative. Only the right column (click anywhere → opens external URL) and a small "View Project" CTA under the center title were interactive.

**Fix — continuous scroll-driven crossfade (replaces AnimatePresence entirely for desktop):**
- Added `computeTransitionStyle(v, index, offset, opts)` (pure function, module scope): given the *continuous* scroll position `v` (a float, e.g. `1.4` = 40% through project 1's dwell — not the stepped integer `activeIndex`), returns `{opacity, scale, blur}` for a given project index. Each project has a fixed 1-unit-wide "dwell" window; inside a configurable fraction `w` (0.35) at each edge of that window it eases in/out (asymmetric scale for a grow-in/shrink-out feel), and for the remaining ~65% of the dwell it's fully settled (opacity 1, scale 1, blur 0).
- `offset` lets one function serve all three zones: `0` = the project's own dwell (center title, mockup), `+1` = plays the "previous title" role in the top zone (visible while the *next* project is centered), `-1` = plays "next title" in the bottom zone. Reusing the same curve shifted by ±1 keeps all zones perfectly in sync without duplicated logic.
- Added a Framer Motion `useMotionValue` called `t` holding this continuous position. It's set every `ScrollTrigger.onUpdate` tick (`t.set(progress * totalProjects)`) alongside the existing `setActiveIndex` — `activeIndex` (React state) is kept for everything that should only change on integer boundaries (URL bar, background gradient, dots, slideshow reset); `t` (not React state — doesn't trigger re-renders) drives the actual visual transition every frame via `useTransform`.
- All three projects for every zone (top/center/bottom titles, mockup) are now **permanently mounted** (no `AnimatePresence`, no conditional rendering) with `SideTitle`, `CenterBlock`, and `MockupCard` subcomponents computing their own opacity/scale/blur/pointer-events from `t` via `useTransform`. Because it's a pure function of real scroll position with no independent timer, nothing can ever be "interrupted" mid-transition — scrubbing fast, slow, or in reverse always looks the same, and there's never a frame where content is fully gone.
- Desktop `AnimatePresence` usage removed for Work section; **mobile layout (`<lg`) was left untouched** and still uses the old discrete `AnimatePresence` per-index approach — same underlying limitation could in principle apply there too, but wasn't in scope for this request. Flagged as a possible follow-up if mobile ever gets the same complaint.
- Performance note: with only 3 projects, permanently mounting all 3 mockups (each with 4 `WaterWave` canvas instances = 12 total) was judged an acceptable tradeoff for eliminating the unmount/remount jank. If more projects are added later, this should switch to a windowed approach (only mount projects within ±1 of `activeIndex`, still driven by the same continuous `t`) to avoid mounting canvases for far-off projects.

**Fix — click-to-navigate:**
- Every title in every zone (`SideTitle`'s `h3`, `CenterBlock`'s `h2`) now has `onClick={() => onNavigate(index)}`, wired to a new `goToProject(targetIndex)` callback.
- `goToProject` reads the live `ScrollTrigger` instance (`stRef.current`, captured when the trigger is created) to compute the pixel scroll position that lands mid-dwell on the target project (`desiredProgress = (targetIndex + 0.5) / totalProjects`, mapped through `st.start`/`st.end`), then calls `lenis.scrollTo(targetScroll, { duration: 1.2 })` using the app-wide Lenis instance (`useLenis()` from `SmoothScroll.js`) so the jump matches the site's smooth-scroll feel everywhere else. ### 2026-08-21 (4) — Reusable magnetic button interaction (site-wide)
Implemented the requested magnetic-hover interaction as a single global, reusable module rather than a per-button React wrapper component, to best satisfy "reusable across the website" + "don't alter existing visual design/layout":

- **New file `components/MagneticButtons.js`** (client component, mounted once in `app/layout.js` alongside `SmoothScroll`/`SideProgressBar`, not per-page). On mount it scans the whole document for any element carrying a `data-magnetic` attribute and wires up the effect — **no other markup, structure, or CSS on those elements is touched**, so existing typography/colors/padding/borders/layout are fully preserved. New elements added later (route changes, conditional renders) are picked up automatically via a `MutationObserver`, no manual re-registration needed.
- **Chose GSAP over framer-motion** (Option B from the spec) for consistency with the rest of the codebase — GSAP is already the established physics/animation library here (`SideProgressBar.js`'s magnetic ball, `useCameraScroll.js`'s ScrollTrigger), and `framer-motion` is only used for `WorkSection.js`'s cross-fade. Uses `gsap.quickTo()` (not `gsap.to()` per mousemove) so repeated pointer updates reuse one interpolating tween instead of spawning a new tween every tick — the standard GSAP pattern for smooth, 60fps-safe continuous pointer-following. `force3D: true` on every tween guarantees `translate3d()` (GPU-accelerated, no layout reflow).
- **Proximity-based, not just hover-based:** rather than only reacting once the cursor is directly over the button (`mouseenter`/`mousemove` scoped to the element), a single shared `window` `mousemove` listener (batched through one `requestAnimationFrame` pass per tick, iterating all registered buttons) computes each button's distance from the cursor to its nearest *edge* (0 if the cursor is already inside), and starts pulling once that's within a configurable radius (`data-magnetic-radius`, default 80px beyond the button's own bounding box) — with a falloff so the pull ramps in smoothly across that ring rather than snapping on at the boundary. This matches the spec's "comes within close proximity or hovers directly over" wording more literally than a hover-only trigger would.
- **Displacement capped** at `data-magnetic-max` (default 20px, spec range 15–25px) via `gsap.utils.clamp`, computed from `(cursor − button center) × strength × falloff`, `strength` tunable per element via `data-magnetic-strength` (default 0.35).
- **Elastic snap-back** on leaving the proximity radius (or the window entirely, via a `document` `mouseleave`): `gsap.to(el, { x: 0, y: 0, duration: 0.8, ease: "elastic.out(1, 0.3)" })` — exact easing/duration from the spec.
- **Optional multi-layer parallax polish, opt-in only:** if a `data-magnetic` element contains a descendant tagged `data-magnetic-inner`, that inner element gets its own `quickTo` pair driven at 1.2x the outer offset (own clamp at `maxOffset × 1.2`) for a subtle layered/3D-depth feel. None of the buttons wired up this session use it (their icon/text isn't in a separate layer), but it's there for any future button that wants it without touching this module.
- **Touch/coarse-pointer guard:** everything is gated behind `window.matchMedia("(hover: hover) and (pointer: fine)")` — if it doesn't match on mount, no listeners are attached at all (zero overhead on touch devices, standard tap behavior fully untouched). Also listens for the media query's own `change` event so it enables/disables live if that ever flips (e.g. devtools responsive-mode toggling, or a hybrid device switching input mode) rather than only checking once at load.
- **Wired up on the 4 existing buttons** in `app/page.js` by adding a bare `data-magnetic` attribute — no other change to those elements: the 3 rounded-full icon links (Contact mail icon, X/Twitter, LinkedIn) and the "Say Hello" mailto pill in the contact section.
- **Not yet verified in the browser by me** (no browser/execute access this session). User should confirm: the pull feels right at the default `strength`/`max`/`radius` values (all first-pass, no authorial spec to tune against beyond the given ranges), the elastic snap-back looks natural, and that nothing regressed on touch/mobile viewports (should be a full no-op there).

### 2026-08-01 (4) — Root cause found: paused AnimationAction silently ignores mixer.setTime()
User reported the new scroll hook (2026-08-01 (3)) still didn't move the camera, but with `[cameraScroll]` console logs showing `progress`/`frame` correctly sweeping 0->110 as they scrolled, and `mixer`/`camera` both truthy -- i.e. the scroll-to-frame math was provably correct, so the bug had to be in how that frame value gets applied.

**Root cause:** `HeroScene.js`'s mixer setup had `action.paused = true` (present since the very first version of this project, carried through every iteration so far -- never actually the bug until now, or more likely always the bug and never isolated before). This is a real Three.js `AnimationAction` internals quirk: `mixer.setTime(t)` resets the action's internal `time` to 0 and then calls `update(t)`, which calls `_updateTimeScale()` -- and that function returns `0` whenever the action is `paused`, which zeroes the delta applied to the clip. Net effect: **a paused action's `setTime()` always evaluates to clip time 0, no matter what value is passed in.** The camera silently never advances past frame 0, while everything upstream (scroll listener, progress math, `mixer.setTime()` call itself) works perfectly -- exactly matching the reported symptom.

**Fix:** removed `action.paused = true` from the mixer setup effect in `HeroScene.js`. Safe to leave unpaused because nothing in this codebase calls `mixer.update()` in a continuous loop (a manually-constructed `AnimationMixer` isn't auto-driven by R3F the way `drei`'s `useAnimations` hook would; only this project's own `mixer.setTime()` calls ever touch it), so there's no risk of the clip "playing" on its own once unpaused.

**Not yet re-verified in the browser by me** (no browser access). This should be the real fix, but user should hard refresh and confirm the camera actually visibly moves now, not just that the console numbers look right (which they already were).
